*[English version / 英文版](DESIGN.md)*

如果只想看一節，就看[核心原則](#核心原則跑得出答案不等於答案是對的)。

## 為什麼要做

LinkedIn 每天出五個謎題。它們會計時，而大家分享的就是那個時間。
用手解本來就是這個遊戲的重點 —— 但「一台電腦到底要怎麼樣才能看懂這個盤面」
這件事，結果比謎題本身有趣太多。

所以目標從來就不是「刷一個快的紀錄」。目標是：
**一個程式能不能看著跟人一樣的那些像素，然後看懂它？**
其他所有設計都是從這裡推出來的。這也是為什麼整個專案裡沒有任何 AI 與 API ——
把截圖丟給視覺模型，等於是用「不回答」來回答這個問題。

這個專案分三個階段長出來，程式的形狀到現在還看得出痕跡：

1. **讀一張手機截圖，印出答案。** 一款謎題（Tango），一支腳本。
2. **五款謎題，包進一個點兩下就能跑的 .exe。** 這一步逼出了
   「通用棋盤偵測」與「各謎題辨識」之間的切割。
3. **直接在瀏覽器上幫你玩。** 這一步生出了整個 `automation/`，
   同時帶來一整類新問題 —— 答案不只要正確，還要**可以被執行**，而且要安全。

## 核心原則：「跑得出答案」不等於「答案是對的」

這是整個程式裡最重要的一個觀念，而且是踩過坑學來的。

早期有一次解 Tango，答案看起來完全合理：每列平衡、沒有三連、每個條件都滿足。
但它是錯的。辨識只找到四個 `=` / `×` 符號中的一個，
求解器很忠實地解了**另一道題** —— 一道剛好也合法的題。

這才是危險的失敗模式。當掉沒關係，你看得到、修得掉。
但一個「錯的、卻自我一致」的答案就很糟糕，尤其當程式接下來要照著它動你的滑鼠。

從這件事長出三道防線，而且用在所有地方：

### 1. 用唯一性當作辨識完整性的檢查

出版的謎題只有一組解。這是關於**題目**的事實，
所以它可以拿來當成對**辨識**的檢驗：

> 如果求解器找得到兩組解，那辨識一定漏掉了某個條件。

所以 Tango、Sudoku、Patches 不只是求解 —— 它們會再要求求解器找出**第二組解**，
只要找得到就拒絕這個答案。這一招能抓到漏掉的 `=` 符號、漏掉的 given、
讀錯的數字，而且完全不需要知道漏掉的是什麼。

```python
# tango.py 的核心概念
solution = solve(model)
model.AddForbidden(solution)      # 「現在去找一個不一樣的」
if solve(model) is not None:
    raise MultipleSolutions       # 代表辨識不完整
```

Queens 與 Zip 不適用這招：只要盤面讀對，它們的答案本來就唯一，
所以改用結構性守門（見下）。

### 2. 結構合理性守門

當**結構**被讀錯時，唯一性檢查幫不上忙。有兩道守門是在特定事故之後補上的：

- **Queens 色塊合理性。** 一個淡色系的 Queens 盤面被誤判成 Patches，
  然後被「解」成一塊蓋滿整個盤面的大矩形 —— 回報成功，
  接著把滑鼠從一個角拖到另一個角。現在 Queens 會驗證它找到的色塊
  剛好是 *n* 個，而且每一塊都是連通的。
- **Patches 標籤數量。** 同一起事故的另一面：Patches 現在在標籤少於三個時
  直接拒絕往下做，因為一個看起來只有一兩個標籤的盤面，幾乎可以確定不是 Patches。

### 3. 先正規化，再換尺度重試

這個專案裡的每一個門檻值，都是在寬度約 794px 的盤面上校準出來的。
同一個盤面在 390px 就會失敗 —— 反鋸齒會吃掉細的符號，`=` 會糊成一團灰。

天真的解法是「每個尺寸各調一組門檻」。真正的解法是讓尺寸這件事消失：

```python
TARGET_BOARD_PIXELS = 794     # 讀之前一律縮放到這個尺寸
MIN_BOARD_PIXELS = 500        # 小於這個就先放大，不要直接相信它
```

流程是：找到棋盤 → 縮放到校準尺寸 → 才開始讀。
當這一輪失敗、**或者成功但解不唯一**時，就用逐步收緊的中央裁切
與更高的預放大倍率重試：

```python
_PRESCALE_STEPS  = (1.0, 1.75, 2.5)
_CROP_FRACTIONS  = (1.0, 0.85, 0.72, 0.6, 0.5)
```

關鍵在於：**成功但解不唯一時，重試迴圈不會停。**
就是這條規則把「它跑出來了」變成「它是對的」。

## 分層：為什麼要有 `core` / `puzzles` / `automation` / `ui`

這些層存在的理由，是「每一層被允許知道什麼」：

| 層 | 知道 | 不知道 |
|---|---|---|
| `core/` | 像素、網格、數字 | 這是哪一款謎題 |
| `puzzles/` | 謎題規則、顏色代表什麼 | 螢幕、滑鼠、GUI |
| `automation/` | 螢幕座標、滑鼠、驗證 | 怎麼解任何一款謎題 |
| `ui/` | 視窗、按鈕、語言 | 影像處理、求解 |

好處是可測試性。`test_solvers.py` 完全不用任何圖片就能跑完整個求解層。
`test_automation.py` 用一個「每格 10 像素」的假棋盤加上預演驅動，
就能驗證精確的點擊次數，過程中滑鼠根本不需要存在。兩者都不需要螢幕。

這同時也代表**只有一個檔案會動滑鼠**（`input_driver.py`）。
任何想點擊的東西都得經過它，所以中止檢查、預演開關、速度倍率
全都只存在於一個地方，而且繞不過去。

### 為什麼用「一款一個模組」而不是類別繼承

每個謎題模組都對外提供同樣的那幾個函式 —— `read_*`、`solve_*`、
以及一份「要怎麼填」的描述 —— 但這五款謎題的內部幾乎沒有任何共同點。
Tango 讀兩種圖示加上邊界符號。Queens 做顏色分群。
Patches 同時要讀數字**和**形狀提示。寫成基底類別的話，
那就是五個特例披著一件風衣假裝是一個人。一張扁平的模組註冊表誠實得多：

```python
PUZZLES = {"tango": tango, "queens": queens, ...}
```

## 辨識：比預期難的那些地方

### 找出網格

最直覺的做法 —— 數格線數量 —— 是錯的。棋盤有很淡的外框，有時偵測得到、
有時偵測不到，所以同一個盤面的格線**數量**會在 n-1 到 n+1 之間跳動。
Patches 盤面就是這樣一直被算少一格。

正確做法是用**間距**而不是數量。就算最外圈那條線漏掉了，
線的位置關係還是穩定的，所以：

```
n = round(棋盤寬度 / 已偵測格線間距的中位數)
```

這對「完全漏掉第一條或最後一條線」是免疫的，而那正是一直在發生的失敗。

### `=` 與 `×` 符號是褐色，不是灰色

Tango 的邊界符號被一個彩度濾波器抹掉了 —— 那個濾波器建立在
「符號是灰的、格子是彩色的」這個假設上。它們不是灰的，
是低彩度的褐色，所以連同背景一起被濾掉了。
把整個偵測改成走 HSV 的 **Value（明度）**通道就解決了。
彩度從一開始就是錯的那個軸。

### 月亮的弧形與黑色外框

月亮是靠找暗色團塊偵測的 —— 而當取樣範圍靠近格子邊緣時，
它也會抓到棋盤自己的黑色外框。解法是取樣時往格子內部縮很多，
並取**中位數**、排除高彩度像素，這樣幾個雜訊邊框像素就動不了結果。

### Queens 皇冠：那個不存在的門檻值

皇冠偵測原本用的是「整格的暗像素比例」，門檻大約 0.17。
在真實盤面上量測後發現：有皇冠的格子是 0.10～0.20，空格子也是 0.10～0.20 ——
訊號的大部分其實來自格線，根本不存在任何一個能分開它們的門檻值。

把取樣區域往內縮 28% 之後，格線完全被排除掉，兩群數值乾淨地分開了：

```python
ICON_INSET_RATIO = 0.28       # 皇冠 0.268-0.374，空格 0.000
```

這個教訓可以推廣：當一個門檻值怎麼挑都挑不出來的時候，
通常是量測本身混進了不該包含的東西。

### 色塊分群：為什麼不用 k-means

Queens 的色塊一開始是用 k-means 分的。它會動 —— 然後就不會動了：
同一個盤面在不同次執行會把某一塊隨機切成兩塊，
因為 k-means 的初始化是隨機的，而兩個淡色系顏色本來就很接近。

改成用出現頻率分群：收集每一格的中位數顏色，依出現次數排序，
然後把和某個已確立顏色距離夠近的都併進去。

```python
SAME_COLOR_EPSILON = 10
```

結果是確定性的，而且不會憑空生出盤面上不存在的色塊。

### Patches：那些看起來很像數字的白色縫隙

Patches 的標籤是疊起來的半透明形狀。那些形狀**之間**的白色縫隙
被當成了數字筆畫 —— 一個真的「4」被切成四塊碎片，
空白標籤被切成三塊。兩者都被判成「讀不出來」，整個辨識就中斷了。

兩個改動修好它：只從標籤中央 62% 的範圍讀數字，
並丟掉高度不到標籤高度 42% 的連通元件。

```python
DIGIT_REGION_RATIO      = 0.62
DIGIT_MIN_HEIGHT_RATIO  = 0.42
```

這裡還埋著第二個教訓。為這個 bug 做的第一個測試素材，
是把整個標籤塗滿做出來的 —— 而那不小心把一個**虛線**標籤變成了**實心**標籤，
於是測試是對著一個現實中不可能出現的盤面通過的。
現在的素材只擦掉中央的數字。**用不可能的輸入寫出來的測試，什麼也證明不了。**

### 不靠 OCR 引擎讀數字

這些數字來自同一個 App、只有幾種尺寸、同一套字型。
這根本不是 OCR 問題，這是查表。字形正規化成 28×28，
再跟從 App 本身擷取出來的樣板比對。不用裝 Tesseract、不用下載模型，
而且它不會把 `4` 讀成 `A` —— 因為表裡面根本沒有 `A`。

## 自動化：答案必須是「可以執行的」

算出正確答案大概只是一半的工作。要把它透過真實滑鼠送進真實網頁，
會生出另一整套失敗模式，而且每一個都是真的在使用過程中發生過的。

### 解完之後還在一直點

最糟的一個。盤面填完之後，網站會用完成畫面把它蓋掉。
驗證補點迴圈接著去重讀那個畫面，發現「該有皇冠的地方沒有皇冠」，
判定填答失敗，於是繼續點。

解法是讓 `verify()` 回報**兩件不同的事**：

- *盤面是錯的* → 補點那幾格
- *盤面已經不在了* → 停止、釋放滑鼠、不要補點

能分辨「錯了」跟「不見了」，才是程式懂得放手的關鍵。
這一點由 `test_stops_when_board_changes` 守著：它把盤面塗掉，
然後驗證補點計畫回傳的是 `None`。

### 它在跟使用者自己的滑鼠搶

原本在自動化開始前會跳一個確認對話框。使用者按下確定，
而自動化 —— 設定成零延遲 —— 就在滑鼠鍵還壓著的時候開始點。
兩邊的輸入交錯在一起，盤面被填得亂七八糟。

兩個改動：確認對話框整個拿掉（這東西的重點就是要省秒數），
然後加上一段刻意的短延遲，以及 `wait_for_mouse_release()`，
在實體滑鼠鍵真的放開之前什麼都不做。

### 網頁跟不上

Zip 是用一次連續拖曳填完的。網頁是靠「指標經過了哪些格子」來決定路徑的 ——
所以從格子中心直接跳到下一個格子中心，中間那些格子就被跳過了，
遊戲會回「您必須按照數字的順序」。

驅動現在會對每次拖曳做插值，讓每一步都不超過 12 像素：

```python
DRAG_MAX_STEP_PX = 12
```

而預設速度倍率則是在看過一段「它跑贏網頁」的螢幕錄影之後，調高到 2.0。

還有一個相關的常數，用在同一格要點兩次的時候：

```python
SAME_SPOT_CLICK_GAP = 0.15    # 同一格連點間的停頓；理由見常數自己的註解
```

### Patches：當「棋盤還定位得到嗎」這個問題問不下去的時候

*（`speed-optimization` 分支，尚未合併回 `main`。）*

填答中途保護的結構性檢查（見上文）有一款謎題它天生服務不好：拼塊。
它自己畫出來的答案會用實心顏色蓋滿棋盤，而那些顏色會抹掉
`detect_grid_size` 依賴的內部格線——不是偶爾抹掉，是永久抹掉，因為填答
只會讓覆蓋範圍越來越大，不會變小。一次真實的 8x8 填答（2026-08-09）
示範了這件事能有多糟：`detect_grid_size` 在一個完全沒有移動過的棋盤上
連續失敗了 7 次（已對照螢幕錄影確認）——遠遠超過 2026-08-06 那次事件
已經調高過、原本要撐住同一個問題較小版本的容忍上限。

打破僵局的關鍵想法是：保護其實不需要「重新推算」格線才能知道棋盤還在。
它從計畫本身就已經知道，自己確切畫了哪些格子、沒畫哪些格子。所以與其問
「我還找得到格線嗎」，不如問一個真正能回答的、範圍更窄的問題：
**棋盤的外框還在嗎？而我們還沒畫過的部分，看起來還是一開始的樣子嗎？**

外框那一半幾乎是不花成本的。`find_board_bbox` 找的是棋盤的「外」輪廓，
我們自己的填色永遠不會碰到它——填色永遠嚴格畫在格子「裡面」。直接對
失敗的那張 8x8 畫面、以及測試組裡每一張已經填了不少的既有測試圖量測過，
外框在每一個內部格線檢查失敗的情況下都還是穩定定位得到。

內容那一半，就是第一次嘗試出錯的地方，值得誠實記下來。第一版量測
「參考畫面裡還沒被填色（我們自己的飽和填色以外）的結構——殘存格線、
標籤數字，任何比背景暗的東西」在目前畫面裡還有多少比例仍然是暗的，
並且用這個分數做兩個決定：分數高代表「還是我們的，繼續」；分數低代表
「不是我們的，立刻中止」——比原本的容忍計數更快出手。一次獨立的
對抗性審查，只看得到程式差異、被要求去推翻它，找到兩個這其實比什麼
都不做更糟的地方：

- 落在特定亮度區間的整片灰階畫面拿到**滿分 1.0**，把保護永久關掉——
  這個指標從來沒有要求「目前畫面」自己要有對比，只要求它比參考畫面的
  背景暗，而任何夠平整的灰色在每一個像素上都同時滿足這一點。
- 重播 2026-08-06 那次真實事件自己的測試圖——正是
  `PATCHES_FAILURE_TOLERANCE=6` 存在的理由——立即中止判決在「第一次」
  檢查就把那次「正確」的填答錯殺了。那組畫面兩次擷取之間有約 1% 的真實
  縮放漂移，小到人眼會認為是同一個棋盤，卻足以把原始分數拖到門檻以下。

兩個發現指向同一個設計錯誤：讓這個新檢查有能力讓保護變得「更嚴格」，
正好會引入這整個專案存在的目的所要避免的那種——自信卻錯誤的判斷。
修法不是換一個更好的數字，是換一個更小的契約。這個檢查現在只可能
**認證**（「內容仍然吻合——把失敗計數歸零」）或**拒絕認證**（「無法
確認——落回原本就存在、完全不變的容忍計數」）。它自己絕不中止任何事：

```python
if use_content_check and reference_content_matches(reference, image):
    consecutive_failures = 0     # 認證通過——延長這次計畫的壽命
    return True
# 拒絕認證，或這裡根本沒開啟這個檢查：以下每一行程式碼，
# 都跟這個功能存在之前逐位元組相同。
consecutive_failures += 1
if consecutive_failures <= failure_tolerance:
    return True
...
```

在這個契約下，每一種情境都可以證明不比改動前的保護差：新程式碼最壞的
結果就是拒絕認證，而那「正是」舊路徑本身。認證本身仍然要通過兩道獨立
量測出來的關卡——結構吻合下限（0.90，對照「自然渲染」下最強的冒牌貨
只拿到 0.76）與對比保留下限（0.85，因為濃度 `a` 的白色遮罩，會把遮罩
內內容的對比精確壓縮成 `1 - a` 倍——這個關係是在真實螢幕擷取上驗證過的，
不是假設出來的）——所以整片灰階畫面、遮罩、或另一塊網格間距剛好相同的
拼塊棋盤，都會被拒絕認證，不會通過。重做之後的複審確認契約成立，只留下
一個誠實記錄下來的殘餘缺口：局部的「深色」去飽和遮擋物，原理上跟我們
自己的深色填色無法區分，因為兩者的讀法完全一樣。曝險以計畫本身的長度
為界，而且是寫進程式碼裡誠實記錄的，不是被含混帶過的。

更廣的教訓超越了這一個保護機制本身：**「說停」的權力，必須跟「說繼續」
的權力分開賺取。** 讓同一個訊號同時做這兩件事，就算理由是「已經很小心
地量測過了」，本質上仍然是拿一個已知、有界的盲點，去換一個沒被量測過的
盲點——而這次唯一抓到這筆交易的方法，是把設計交給一群唯一任務就是
「把它弄壞」的審查者，趕在它真正碰到一位使用者還在努力解完的題目之前。

### 等待一個本來就不可能被找到的棋盤

*（`speed-optimization` 分支，尚未合併回 `main`。）*

2026-08-10 有一次執行的記錄檔顯示連續輪詢了 68 秒——353 次檢查，大約每
190 毫秒一次，時間點完全正常——卻一次都沒有偵測到棋盤。事後回放同一
範圍的螢幕錄影，畫面上真正的 Patches 棋盤其實停在那裡、完全沒被動過，
超過十秒。這不是時間點剛好沒對上，也不是輪詢太慢：這個迴圈完全照設計
在跑、頻率也完全照設計——只是它拿去檢查的內容，不管再檢查幾次，
用的那套偵測邏輯本來就不可能接受它。

找到這個問題靠的習慣，是不單獨相信 log 的空白、也不單獨相信錄影畫面，
而是往下再多降一層：存下「等待迴圈自己的擷取路徑」真正產生出來的
位元組（面板上的「測範圍」按鈕本來就是為此存在的，只是在迴圈默默失敗
的那段時間裡從來沒被用到），拿這份位元組、而不是同一範圍的螢幕錄影，
手動餵給同一套偵測邏輯。這兩者並不能互相替代。錄影在原始解析度下毫無
困難地定位到棋盤；而程式自己的擷取——理論上是同一時刻同一畫面——卻
定位不到。真實擷取上 `find_board_bbox` 找到的最大輪廓只有 7,980 平方
像素——就是幾顆數字標籤，沒有別的——而一個棋盤大小的輪廓需要佔到畫面
面積的 15%。棋盤自己的外框線，在原始擷取解析度的絕對像素數下太淡，
固定半徑的 Canny 加膨脹演算法，不管跑幾次都接不成一圈完整的形狀。

值得多想一下的是：這個確切的失敗模式，早就在另一個完全不同的函式裡
被寫下來、取過名字了。`_locate_board`——`solve_image()` 自己真正要
求解時所用的定位器——它的文件字串一開頭就寫「淡色邊框在原尺寸抓不到時
先放大再找」，而且有一個為了這件事而做的三階放大階梯撐腰。而**這個
便宜的預先檢查**——決定「什麼時候該開始求解」的那一段——是後來為了
另一個完全不同的理由（反應時間，不是正確性——為什麼它存在，見「網頁
跟不上」那一段）獨立寫出來的，它重新推導了一遍「這裡有沒有棋盤」這個
問題，而不是沿用比較慢的那條路徑早就得到的答案。而且它推導得**不完整**：
只試了一種倍率，不是三種。這個缺口從來沒有被任何一張測試圖踩到過，
因為到那之前收集到的每一張測試圖，剛好外框在 1 倍下都撐得住——包括
大部分時候的 Patches。撐不住的那一張，就這樣一直沒被測到，直到真的有
一次執行踩中了它，而且有人存下「真正的擷取」而不是它的替代品，直接
拿去檢視。

修法是把 `_locate_board` 三階裡的其中一階補回來——1 倍下找不到時，
用 1.75 倍重試一次——實測最壞情況 150.9 毫秒，之前是 30.0 毫秒，
仍然舒服地落在輪詢的時間預算內，而且只有畫面上真的還什麼都沒有時才
會付這筆成本。更廣的教訓，重點不在放大倍率本身，而在「該信任什麼」：
「同一個」範圍的螢幕錄影，錄到的是一個人站在那裡會看到什麼，不是程式
自己的擷取路徑真正收到了什麼——這兩者可能悄悄地分歧。當一個偵測器的
行為沒辦法用它自己的程式碼解釋時，下一步不是去看螢幕錄影——是去看
偵測器自己當時真正拿到的是什麼。

### 上一題留下來的游標

*（`speed-optimization` 分支，尚未合併回 `main`。）*

一次真實的 2026-08-12 Queens 棋盤失敗在「色塊分群結果不合理」——其中
一個色塊被讀成拆成 31 格的主體加上不相連的 4 格孤島，另外還有一格單獨
量到了完全不同的第三種顏色。棋盤本身沒有任何異常；存下來的失敗截圖
（見上兩節的診斷存檔）在人眼看來就是八個乾淨、成形良好的色塊。色塊判讀
（見上面「色塊分群：為什麼不用 k-means」）設計上就是單純照量到的顏色
分群——這是唯一一種真的撐過對這個專案實際配色測試的做法——而同一套
設計沒有辦法分辨「這格顏色因為某個原因變了」跟「這格真的是不同色塊」。

顏色為什麼會變，其實整段時間都在畫面上，對照擷取那一刻的螢幕錄影就
看到了：OS 的滑鼠游標剛好停在棋盤上。LinkedIn 會把指標底下那格的顏色
變深——這是正常的 `:hover` 樣式，不是他們那邊的問題——而連續模式是
從一題直接接到偵測下一題，還沒有自己的任何一次點擊，去把游標從「上一題
最後一次點擊」留下的位置挪開。相鄰兩題常常畫在螢幕上很接近的座標，
所以那個殘留的位置常常剛好落在新棋盤上。

不管怎麼調整顏色比對的容忍度都解決不了這個問題——這個歧義在像素層級
是真實存在的：對一個純粹靠顏色判讀的程式來說，被 hover 變深的格子跟
真的不同色塊，是同一種證據。修法是把成因拿掉，而不是想辦法事後偵測
它的影響：在真正要拿去讀的那次擷取之前，先把游標移出棋盤——這呼應了
這個程式碼庫裡已經有的、給另一個「疊在同一個位置上」的角色用的做法——
`_keep_window_clear_of_capture()` 存在的原因，是這個程式**自己的**視窗
在整個 2026-08-08 的執行過程中疊在 Sudoku 棋盤上，悄悄擋住了一整欄的
原始數字。`InputDriver.park(x, y)`（唯一可以動滑鼠的檔案）就是游標版的
對應做法：只移動、不點擊，然後 `_round()` 會在 solve_image 真正開始跑
之前重新擷取一次。跟視窗清空函式同一套「靠在擷取矩形旁邊，角落是最後
手段」的定位邏輯，刻意維持同樣的形狀，這樣兩者才不會悄悄對「清空」這件
事有不同的認定——只多了一個視窗那邊不需要的細節：角落備案會偏移
`PARK_MARGIN_PX`，不會停在角落像素本身，因為那個確切的像素正是
pyautogui 自己的 FAILSAFE 會中止執行的地方，閃開一種失敗模式卻落到
另一種上面，稱不上是修好了。

### 接續填一半的盤面

如果使用者已經放了幾個皇冠，或是自動化中途被打斷，
填答計畫就必須考慮螢幕上現在有什麼。Queens 的格子循環是
空白 → X → 皇冠，所以顯示 X 的格子只要再點一下、不是兩下，
而放錯位置的皇冠必須先清掉。`players.py` 會讀出目前狀態，
逐格算出需要的點擊次數，而不是假設盤面是空的。

## 多語系

所有會被使用者看到的字串，都經過一張以短名稱為鍵的扁平字典，
每個鍵有 `en` 與 `zh` 兩個值，UI 持有一個 `Translator` 物件：

```python
t = Translator("zh")
t("btn_solve")        # "自動解答"
```

用扁平而不是巢狀，因為巢狀買到的結構沒有人真的需要，
反而讓漏掉的鍵更難被發現。語言設定會被保存下來，重開之後還在。

原始碼的註解做成雙語，理由跟 UI 一樣：這個專案是要放出去給別人看的，
英文那一半讓專案能被搜尋到、能被別人拿去用，
中文那一半讓作者自己維護得下去。

## 刻意沒有做的事

- **不用 AI 或視覺模型。** 用「問一個模型」去回答「程式能不能看懂這張圖」，
  等於是在回答錯的問題。
- **不做 DOM 自動化。** 直接讀網頁的 HTML 會比讀像素簡單太多也穩太多。
  但那樣有趣的部分就消失了，而且會變成依賴 LinkedIn 的 markup，
  而不是依賴螢幕上真正呈現的東西。
- **不做框選 UI。** 早期版本讓使用者拖一個框把棋盤圈起來。
  它會建立第二個 Tk root 視窗，然後把整個程式一起帶走。
  後來換成自動偵測棋盤，這樣本來就比較好 ——
  程式自己看得到棋盤在哪，就不該叫使用者告訴它。
- **不做門檻值的設定檔。** 這個專案裡每一個門檻值都是從真實盤面量測出來的，
  而且量到的數值就寫在旁邊。把它們開放成設定，等於是在邀請大家用猜的去調。
