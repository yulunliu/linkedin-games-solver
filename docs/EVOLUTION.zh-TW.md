# 專案演進

從第一次以單一專案發布（1.0.0）到 `speed-optimization` 分支合併，依主題
整理這個專案變成了什麼樣子。跟按時間、照版本編號寫的
[CHANGELOG.md](../CHANGELOG.md) 不同，這份文件把每一項真實的改動依照
「解決的是哪一類問題」分組——不用讀完一整年的日期條目，也能大致掌握這個
專案的樣貌。精確的技術細節、數字、跟每個修正背後的故事，都留在
CHANGELOG.md 裡；這一頁是地圖，不是疆域本身。

---

## 辨識準確度與範本校準

在真實螢幕上、第一次就把數字、顏色或棋盤格數讀對，不是只在合成測試案例
上過關。

- **數字範本 0 與 7 不再依賴機器上裝了哪些字型。** 以前是在 import 時從
  `C:/Windows/Fonts` 算繪出來的——沒裝那些字型的機器上根本不存在，
  比對時就會用高信心挑一個最接近的「錯」數字。現在兩者都以位元組烘焙進
  原始碼，涵蓋範圍不再因機器而異。
- **數字分類加上了差距檢查。** 光看分數分不出對錯——曾經有一次誤讀拿到
  的分數，比很多正確比對還高。現在字形只有在第二名確實落後一段量測過的
  距離時才會被接受，否則回報成讀不出來，而不是用猜的。
- **Patches 的差距門檻，對它最難分辨的那一組數字而言物理上不可能通過**，
  後來換成用 13,000 個真實字型樣本量測出來的相對規則，不會擋掉任何一個
  舊的絕對門檻以前意外放行的錯誤。
- **Zip 的圓點偵測與數字內孔處理都修好了**——實測發現數字比較寬的圓盤
  會被漏掉（「10」對「1」），填實內孔後的「0」也曾經只差一點就被誤讀成
  「9」。
- **Sudoku 的候選數字縮小到棋盤實際可能出現的範圍**（6x6 只有 1-6），
  這免費讓每個字形的差距明顯變寬——後來這個技巧也被重新拿來評估是否
  適用於 Zip 與 Patches。
- **兩次題目類型誤判都是從真實執行記錄找到根因、修好的，不是用猜的**：
  一個是 Sudoku 棋盤的顏色比例剛好卡在 Tango 分支門檻底下，另一個是 Zip
  棋盤的路徑顏色也發生同樣的事——每次誤判都要白燒 5-9 秒，等錯誤的一整條
  求解階梯跑到耗盡，才會靠備援機制找到正確類型。
- **一份持續累積的真實數字素材庫，現在會自己成長。** Sudoku 填答後的
  驗證步驟本來就會重讀每一格自己打上去的數字，讀不出來的那一格（真值
  可信——就是我們自己的求解器選中的那個數字）會被存成校準候選資料。
  後來擴充成：只要 Sudoku/Zip/Patches 求解成功，都會把「填答前的乾淨
  畫面」跟「算出來的答案疊圖」存成一對——這是未來把目前共用的辨識門檻
  拆分成各題目獨立版本所需要的素材，會先經過人工檢視才會回頭餵進範本。

## 自動化安全機制

滑鼠在動的時候盯著畫面看、拒絕對一個已經變了的棋盤採取行動的那些機制。

- **每一款題目的求解結果都加上了唯一性或合理性守門**——Tango、Sudoku、
  Patches 拒絕第二組合法解；Queens 拒絕無法剛好組成 *n* 塊連通色塊的
  顏色讀法；Patches 拒絕少於 3 個標籤。辨識讀錯現在會大聲失敗，
  而不是自信地點下一個看起來合理、但其實錯誤的答案。
- **填答計畫進行中會有盤面守衛盯著畫面。** 以前計畫一旦開始，就再也不會
  看畫面直到整個跑完——實測過的盲點最長到 21 秒——網站中途換上完成畫面，
  剩下的每一次點擊就都落在它上面。守衛現在會在動作之間問一次結構性的
  問題，並且節流以維持低成本。
- **守衛自己撐過了兩輪針對「自己誤判」的強化。** Patches 自己畫出來的
  填色，一旦蓋住足夠面積就會打敗守衛的結構性格線檢查；一道遮色備援、
  後來一道內容比對檢查（驗證過只會「認證」或「拒絕認證」，自己絕不
  中止任何事）補上了這個缺口，同時沒有讓守衛原本要防的誤判重新出現。
  最終設計是被一次獨立的對抗性審查重新塑形的——審查者在第一版上線前
  就找到了真正的反例（整片灰階畫面、同尺寸的另一塊棋盤）。
- **守衛跟填答後的驗證都學到了「棋盤只是移動了」不等於「沒有改變」**——
  兩者以前都只用格子索引比對，對平移完全不敏感，一個往下移了 80px 的
  棋盤照樣被判定沒有改變。
- **CLI 的全自動路徑現在跟 GUI 共用同一個守衛**，補上了 `--go` 以前
  完全沒有任何保護就能跑完整個計畫的缺口。
- **守衛觸發的中止曾經會讓整個連續模式悄悄結束**，而不是繼續下一題——
  原因是中止那一輪跟緊接著的等待步驟共用了同一個停止旗標鎖定。已修正，
  而且用一個「先在沒修正的程式碼上跑過、確認真的會像事故一樣失敗，
  才證明修正真的有效」的測試驗證過。

## 解題速度優化

把「最終算得出答案」變成「一秒內算出答案」，每次改動都先量測、再改、
再量測，絕不犧牲任何安全檢查。

- **工作影像長邊有上限**——放大不會替辨識器增加任何可用的資訊，多花
  成本處理超過這個尺寸的像素只會拖慢後面每一步。
- **盤面守衛會自我節流**，在一小段時間內沿用上一次的答案，不是每個
  動作都重新評估——不節流的話，一輪五題單純檢查的成本就超過一分鐘。
- **連續模式把「一天按五次求解」變成「按一次」。** 迴圈現在會自己等
  題目出現、求解、填答、等棋盤離開、重複——補上了一個真實的缺口：
  忘記在下一題開始前再按一次按鈕，浪費的時間比這個功能省下來的還多。
- **「先等按鈕、題目還沒出現就先準備好」的啟動流程**、好幾個新的速度
  檔位、以及一輪把真實執行記錄裡量到的死等節點通通削掉的整理（包含
  一次真實誤判之後才調高的 Patches 守衛容忍度），各自都從一天一輪的
  五題實測中省下了真實、有記錄可查的秒數——其中一個後來發現對真實遊玩
  太激進的檔位，也刻意被拉回去，沒有為了數字好看而硬留著。
- **Zip 與 Patches 刻意跳過填答後的驗證**，因為兩者都沒辦法逐格讀回來
  （答案是畫出來的路徑或一組上色的矩形）——硬要驗證也只是白付一次
  等重畫加重新擷取的成本，換不到任何有意義的檢查結果。

## 使用者體驗與工作流程

盯著畫面看的人真正會注意到的部分。

- **滑鼠現在每次擷取前都會停到棋盤外面**，不只是點擊前才閃開。
  LinkedIn 自己的 `:hover` 樣式會讓游標底下那格顏色變深，而以顏色為準的
  Queens 判讀沒辦法把這個跟真正的色塊邊界分開——這是從一次真實執行
  找到根因的：游標繼承了上一題最後一次點擊留下的位置。
- **GUI 視窗現在會自動閃避自己的擷取範圍**，而且在真正需要使用者注意
  時（連續失敗、解析度不符）會立刻還原，不會維持連續模式平常那種
  縮到最小的狀態。
- **從第一次發布就有中英文雙語介面與文件**——中英文切換設定會被保存，
  而且每一行原始碼註解都用兩種語言寫，這是整個專案的規則，不是事後
  才想到的。
- **存起來的擷取範圍，現在會在校準當下的螢幕已經改變時提醒（但不會
  擋住執行）**——換螢幕、換解析度、改 Windows 顯示縮放比例，以前除了
  一句籠統的「找不到棋盤」之外什麼提示都沒有。

## 診斷與除錯工具

因為真正的目標謎題一天只會重置一次，沒有「這次記錄不夠、明天再多加點
記錄重跑一次」的餘地——一次遊玩就必須留下足夠的證據，事後才問得出問題。

- **一份帶時間戳記、只增不改的動作記錄**，記下每一次點擊、每一次守衛
  檢查（包含以前完全看不到的驚險時刻）、每一次辨識嘗試——從一開始執行
  就顯示在畫面上，讓螢幕錄影從第一格就拍得到記錄檔的路徑。
- **求解重試全部用盡時，會存下失敗當下實際用的那張擷取畫面**，守衛也會
  存下觸發中止的那一張——同一個想法套用在兩種不同的失敗形狀上，補的是
  同一個缺口：事後查不出根因，因為沒有任何東西留住辨識器當時實際看到的
  真實位元組。
- **兩個存圖資料夾刻意服務兩種不同的對象。** `img/` 是人主動選擇留下、
  回報問題時會去看的地方；`calibration_candidates/` 是程式自動、沒被
  要求就寫入的，目的就是留給之後人工檢視、再決定要不要餵進校準工具——
  混在一起會讓自動寫入的東西看起來像是使用者自己存的。
- **一個可選的環境變數覆寫，讓本機好幾份 checkout 能共用同一個訓練用
  資料夾**，不用各自累積一份獨立的記錄與截圖——沒有設定時（已發布 exe
  的每一個一般使用者都是這樣），行為完全不變。

## 穩定性修正

每一項都是從真實的擷取畫面、記錄檔或錄影裡找到根因，不是憑空推論出來的
真實事故。

- **舊結果可能把答案存到新截圖上**——選了新圖片卻還沒求解，上一題的
  結果原封不動留著，存圖就會把舊答案悄悄存成新檔名。
- **填答途中關閉視窗，可能讓滑鼠鍵維持在按下的狀態**，因為工作執行緒
  在自己的 `mouseUp` 清理程式碼有機會執行之前就被砍掉了。
- **就算是完全不會碰螢幕的圖片模式，GUI 也曾經因為缺一個可選的螢幕擷取
  套件而開不起來。**
- **設定檔裡型別錯誤的值，曾經會讓 GUI 一啟動就當掉**，除了手改設定檔
  之外沒有別的辦法回得去。
- **求解沒有時間預算，「停止」中斷不了正在進行中的求解**——一次大尺寸
  螢幕擷取可能要跑上半分鐘，這整段時間完全沒有任何檢查點。
- **原始解析度下太淡、偵測不到的棋盤，靠著在第二個縮放倍率重試修好
  了**——根因來自一次連續輪詢超過一分鐘的執行記錄，而另外獨立存下的
  原始擷取畫面確認棋盤整段時間確實都在畫面上（同一範圍的螢幕錄影不是
  同一份位元組，看起來完全正常——這正是這個專案把「錄影」跟「即時擷取」
  當成兩種不同證據來源的原因）。
