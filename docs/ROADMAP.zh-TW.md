## 六、極端與異常稽核找到的缺陷

對六個攻擊面做的系統性稽核 —— 畸形影像輸入、異常介面操作、自動化路徑、
求解器邊界、惡劣環境、並行狀況 —— 產出 **21 個經獨立複驗仍成立的缺陷**。
1.1.0 修掉四個（Queens 缺唯一性檢查、Patches 呼叫錯求解器、
守衛在拖曳途中中斷、縮圖造成座標不同步），**剩下這十七個還開著**。

完整列出來，是為了讓任何人不必重新發現一次。排序依據是
「哪一個最會擋住『一次玩完五題、全程自動控制滑鼠』」。

### 會產生安靜的錯誤答案

**S1. 換掉底下那張圖時，`self.result` 沒有被清空。**
`_on_pick_image` 與 `_on_test_region` 都會換掉 `self.shot` 卻不清 `self.result`，
而 `_on_save` 只檢查「有沒有結果」。選 A 題、解出來、再選 B 題、按存圖 ——
存出來的是 **A 的答案畫在 B 的截圖上**，用 B 的檔名，對話框還說「已儲存」。
螢幕模式下兩張擷取來自同一個範圍，舊符號會剛好落在新格子正中央，看起來完全合理。
這比聽起來嚴重：存圖是這個專案文件裡寫明的回報管道。
*修法*：`_run()` 開頭與兩個 handler 結尾都清掉 `result`／`mapper`／`plan`；
再給結果蓋上來源影像的識別，存圖時對不上就拒絕。

### 會產生錯誤的滑鼠動作

**W1. 盤面「移動」時，守衛與 `verify()` 都會通過。**
`still_there()` 問的是「盤面還在不在」，從來沒問「還在不在原位」；
而驗證器是用格子的**索引**比對，那對平移是免疫的。
實測：9×9、格子 89px 的盤面往下移 80px —— 守衛說在、`verify` 說
`board_changed=False`，接著補點計畫按下去的那個像素已經屬於另一格。
從 −120px 掃到 +300px，`verify` 在任何位移下都沒察覺。
在 9～21 秒的填答過程中，捲動頁面、移動視窗、改變大小、
或 LinkedIn 的卡片自己長高，都會踩到。
*修法*：擷取本來就是照**預期的矩形**抓的，所以找到的盤面必須落在 ~(0,0)
且尺寸相符，偏超過 0.3 格就拒絕；各驗證器則要拿新的 `board_bbox`
跟 `result.grid.board_bbox` 比對。

**W2. `ui/cli.py --go` 完全沒有盤面守衛。**
整套 `board_watch` 保護只存在於 GUI。實測一個「動了 3 步之後盤面被換掉」的
腳本畫面：GUI 走了 3/28 步就停，CLI **28 步全部走完，其中 25 步落在新盤面上**。
`--go` 是這個專案最接近「五題全自動」的東西，卻正好是唯一盲目執行的路徑。
*修法*：把 GUI 那段 arm 的邏輯抽成
`board_watch.attach(driver, mapper, result, image)`，讓第三個呼叫者沒機會忘記。

**W3. 填答途中關掉視窗，工作執行緒會在 `mouseUp` 之前被殺掉。**
工作執行緒是 daemon，而 `WM_DELETE_WINDOW` 既不停止也不 join，
所以 `drag_path` 的 `finally: mouseUp()` 不會執行。
用假的 pyautogui 追蹤：MOUSE_DOWN 1、MOUSE_UP 0，行程結束後仍然沒有 UP。
按「停止」則會得到乾淨的一組 down/up，所以這是關視窗這條路徑專有的。
「實體按鍵卡住」這個後果是推論出來的，不是觀察到的 —— 但機制成立。
*修法*：關閉時先 `driver.stop()`、帶 timeout join、再 destroy；
並讓 `_ui()` 擋掉 `RuntimeError`／`TclError`。

### 會當掉

**C1. 沒有 `mss` 就開不了 GUI —— 即使是圖片模式。**
第一次執行時 `DEFAULTS["region"]` 是 None，`_apply_settings` 因此一定會呼叫
`default_region()`，而那裡面會 `import mss`。README 與 `pyproject` 都寫著
圖片模式不需要 `mss` 或 `pyautogui`，也有一個測試宣稱在把關 ——
但那個測試只**匯入**模組，而匯入是好的，**建構 app 才會爆**。
**那個測試是一個假的安全訊號。**
*修法*：`default_region()` 裡把 `primary_monitor()` 包起來、退回固定矩形；
測試改成真的去建構 `SolverApp`。

**C2. 設定檔裡的 `region` 型別錯誤會讓 GUI 開不起來。**
`settings.load()` 只過濾鍵、不驗證型別，`_apply_settings` 接著對拿到的東西做
`str(int(v))`。試了八種不同的形狀，每一種都會拋例外。
在打包好的視窗版 exe 上，這就是「點兩下，什麼都沒發生」。
而且踩得到 —— `fullscreen` 根本沒有介面，手改設定檔是使用那個功能的唯一方式。
*修法*：在 `load()` 現有的 `try` 裡把 `region` 強制轉成剛好四個整數，否則丟掉。

### 慢或困惑

**T1. 沒有任何時間預算，而且「停止」中斷不了求解。**
`solve_image` 沒有時限也沒有取消機制。4K 全螢幕擷取要 29～49 秒，
8000×8000 要 238～312 秒。求解中按停止，狀態列會停在「停止中…」19～22 秒。
沒有真的無限卡住，每個案例都正確回報 `ok=False`，所以這是慢而不是壞掉 ——
但在計時的遊戲裡，安靜跟當機分不出來。
*修法*：一開始就縮圖一次而不是每一階都縮、給 `solve_image` 一個
`should_continue` 回呼、並回報現在跑到哪一階。

這十項都**不會**產生錯誤答案或點到錯的格子。它們是白做工、掉設定、或說明得很爛。

## 一、螢幕模式假設了特定一台顯示器

### 目前狀況

螢幕擷取已經避開了最糟的寫死。`capture.py` 是靠「找出包含螢幕原點 `(0, 0)`
的那台顯示器」來判斷主螢幕的，因為在多螢幕環境下 `mss.monitors[1]`
**不一定**是主螢幕。預設擷取矩形接著是相對於那台顯示器算出來的，
而不是絕對座標：

```python
def default_region():
    monitor = primary_monitor()
    left = monitor["left"] + (monitor["width"] - DEFAULT_REGION_WIDTH) // 2
    top  = monitor["top"] + DEFAULT_REGION_TOP
    return left, top, DEFAULT_REGION_WIDTH, DEFAULT_REGION_HEIGHT
```

所以換一台不同解析度的主螢幕它還是能活，其他情況則可以在介面上手動調整範圍。

### 還有什麼問題

- **預設的大小與垂直位移是從一套環境猜出來的**：y = 200 處的 640 × 700。
  在 4K 螢幕上，或瀏覽器縮放比例不同時，棋盤根本不在那裡，
  使用者得自己動手修。
- **第二台螢幕上的棋盤永遠找不到。** 擷取被限制在主螢幕，
  沒有跨螢幕的搜尋。
- **沒有處理 Windows 顯示縮放。** 在 125% 或 150% DPI 縮放下，
  `mss` 與 `pyautogui` 對「一個像素」的認知可能不一致 ——
  擷取是對的，但點擊會偏掉一點。

### 計畫

1. **改成「自己找到棋盤」而不是「被告知棋盤在哪」。**
   `core/board.py` 裡的棋盤偵測本來就能在任意影像中定位出棋盤。
   做法是：擷取整個虛擬桌面 → 在縮小的副本上跑偵測 →
   再用全解析度重新擷取找到的那一塊區域。
   這會讓範圍設定完全從正常流程中消失，只保留成手動覆寫的選項。
2. **搜尋每一台螢幕。** `mss.monitors[0]` 是所有顯示器的聯集；
   在那上面做偵測再把結果映射回去，只要第 1 步做好了，
   多螢幕支援幾乎是免費的。
3. **把 DPI 縮放明確處理掉。** 透過 `SetProcessDpiAwareness`
   宣告行程為 per-monitor DPI aware，然後在啟動時做一次驗證：
   讓一個已知的螢幕座標經過「擷取再換算回來」的來回，確認結果一致 ——
   不一致的話要大聲警告，而不是默默地點偏 30px。
4. **記住上次棋盤出現的位置。** 把上次成功的範圍快取進設定並優先嘗試，
   讓常見情境保持快速。

第 1 步是關鍵；第 2、4 步是它的附帶結果。

## 二、圖片模式是照 iPhone 13 Pro 的截圖校準的

### 目前狀況

這條流程其實**沒有**表面看起來那麼依賴解析度。
每個棋盤在套用任何門檻值之前，都會先被縮放到固定尺寸：

```python
TARGET_BOARD_PIXELS = 794     # 所有校準都是在這個尺寸做的
MIN_BOARD_PIXELS = 500        # 小於這個就先放大，不要直接相信它
```

而當第一輪失敗、或產生非唯一解時，會用其他預放大倍率與中央裁切重試。
這就是為什麼同一份程式能同時讀 1170 × 2532 的手機截圖與電腦瀏覽器的擷取。

### 還有什麼問題

有三件事確實綁在那支提供測試素材的手機上：

- **數字樣板。** `core/digit_templates.py` 裝的是從單一 App 繪製結果、
  幾種尺寸擷取出來的字形。比對之前會正規化成 28 × 28，
  所以尺寸差一點沒關係 —— 但不同的字重、更重的反鋸齒、
  或是筆畫比例不同的裝置，就會開始比對失敗。
  這些現在會**失敗**而不是亂猜（`digits.py` 的差距檢查會拒絕第二名貼太近的字形），
  但失敗終究是失敗：解法是 `tools/calibrate_digits.py`，
  而它需要那台裝置的截圖。
- **0 與 7 從來沒有在真實盤面上出現過。** 沒有任何測試素材含有它們，
  所以這兩個範本來自字型。它們已經烘焙進原始碼、涵蓋範圍不再因機器而異，
  但從未對照 App 實際的繪製結果驗證過。
- **裁切比例。** `_CROP_FRACTIONS = (1.0, 0.85, 0.72, 0.6, 0.5)`
  是量測 iPhone 13 Pro 截圖裡「棋盤 vs 狀態列、瀏海區、App 自身介面」
  的佔比之後挑出來的。平板截圖、或比例差很多的手機，
  可能需要一個不在這張清單裡的裁切比例。
- **顏色門檻假設了手機 App 的配色。** `detect_type.py` 與 `queens.py`
  都是對著這個 App 的顏色校準的。LinkedIn 已經出過一次淡色系的
  Queens 變體，當時就把類型判斷弄壞了；
  修正後的做法（角落填滿覆蓋率）比它取代掉的彩度檢查穩健得多，
  但它仍然是一個固定的數字。

### 計畫

1. **讓門檻值從影像本身推算，而不是寫成常數。**
   這些門檻大多其實是在問「這一格有沒有明顯比棋盤背景更暗／更飽和？」
   先量出棋盤自己的背景，再把門檻表達成相對於它的值，
   就能擺脫對特定繪製結果的依賴。這是本節裡 CP 值最高的一項改動。
2. **不靠裁切清單也能偵測棋盤。** 裁切比例存在的目的，
   是在截圖含有大量非棋盤內容時幫助偵測。
   一個更強的偵測器 —— 找出接近正方形、且內部具有網格結構的最大四邊形輪廓 ——
   可以直接找到棋盤，讓那串裁切階梯從「必要條件」降級成「備援」。
3. **要說出是「哪一個」字形讀不出來。** 辨識現在會拒絕猜測模稜兩可的數字，
   但產生的訊息很籠統。「(3,4) 這個標籤的數字讀不出來」可以直接告訴使用者
   要看哪裡、以及回報問題時要附什麼。這個資訊在失敗當下本來就有，
   只是沒有帶出來。
4. **收集其他裝置的測試素材。** 上面這些在沒有 Android 手機、iPad、
   非 Retina 桌機的測試圖之前，全部都只是推測。
   `tests/test_recognition.py` 的結構讓「加一張素材」很便宜，
   而 `tools/calibrate_digits.py` 可以用一行指令把新裝置的截圖變成範本。

這份文件初稿之後已完成：`tools/calibrate_digits.py` 已經補上，
數字 0 與 7 也已經烘焙進原始碼，不再是 import 時從 Windows 字型算繪 ——
見 [CHANGELOG.md](../CHANGELOG.md)。

## 三、檢查補點沒有涵蓋 Zip 與 Patches

### 目前狀況

填完之後，`verify()` 會重讀盤面，然後不是補點錯掉的格子、
就是因為盤面不見了而停止。但派工表裡只有三個項目：

```python
_VERIFIERS = {queens.KEY: _verify_queens, tango.KEY: _verify_tango, sudoku.KEY: _verify_sudoku}
```

Zip 與 Patches 會落到 `supported=False`，意思是：不檢查、不補點，
連「盤面已改變」也偵測不到。

### 為什麼這件事重要

這兩款正是用**拖曳**填答的 —— 也就是最容易出錯的那兩款。
「網頁沒跟上的拖曳」正是 `DRAG_MAX_STEP_PX` 與速度倍率想要緩解的失敗模式，
而它偏偏就是唯一沒有任何東西去驗證結果的情況。程式會回報成功然後停止。

這不是把大缺口說成小缺口：五款謎題中有兩款，
整個設計所倚賴的那張安全網根本不存在。

### 計畫

1. **把 Zip 的路徑讀回來。** 畫出來的路徑是一條粗的彩色線；
   對每一對相鄰格子的交界取樣，就能知道那一段有沒有被畫出來。
   跟預期路徑比對，既是正確性檢查，也能指出拖曳是在哪裡斷掉的。
2. **把 Patches 的切法讀回來。** 完成的矩形有可見的外框；
   現有的標籤偵測本來就能找到每個標籤，
   所以「檢查每個標籤是否落在一個正確大小的矩形裡」跟 `find_labels`
   現在做的事很接近。
3. **至少讓五款都能偵測盤面已改變。** 就算沒有逐格驗證，
   「發現盤面不見了」的成本很低，而且能讓 Zip 與 Patches 乾淨地停下來，
   而不是單純因為動作做完了才停。

第 3 項很小，而且應該先做。

## 四、錯誤訊息不受語言設定影響

### 問題是什麼

`i18n.py` 會翻譯介面，但辨識與求解的錯誤是在失敗當下組出來的、
寫死的中英串接字串：

```python
return failure(KEY, "no solution / 找不到符合規則的解", grid=grid, info=info)
```

`result.info` 也一樣 —— 棋盤大小、色塊數量、標籤數量。
這些字串直接進到記錄區，完全沒有經過翻譯器。

### 為什麼這件事重要

把介面切成英文並不會把錯誤文字也切成英文。所以英文使用者會在
「訊息最需要清楚」的那個地方看到中文：也就是出事的當下、
他最需要知道該怎麼辦的時候。「介面可以切換語言」這項需求因此只做到一半。

這是完成度問題，不是正確性問題 —— 訊息仍然讀得懂，只是不是使用者選的語言。

### 計畫

1. **改成回傳「鍵 + 參數」而不是已格式化的字串。**
   `failure()` 與 `info.append()` 改成接收類似 `("err_no_solution", {})` 或
   `("info_board_size", {"n": 6})` 的東西，由介面在顯示時用它本來就持有的
   翻譯器格式化。
2. **把這些鍵加進 `i18n.py`** —— 大約 25 個新項目，
   沿用現有的扁平 `{鍵: {語言: 文字}}` 結構。
3. **命令列要保留純文字的備援**，因為 `--image` 在載入任何設定之前
   就可能需要輸出訊息，那時還沒有翻譯器。

這是機械性的工作，但會動到每一個謎題模組與兩個介面。
它還沒做的原因是這個廣度，不是因為困難。

## 五、0 與 7 的範本從未見過真實盤面

### 問題是什麼

`tests/fixtures/` 裡沒有任何一張截圖含有 `0` 或 `7`。
所以這兩個數字範本是用系統字型算繪出來的，不是從 App 擷取的。

它們現在已經以位元組烘焙進原始碼，不再是 import 時才算繪 ——
所以涵蓋範圍不再取決於機器上有哪些字型，那原本是一個真的 bug
（見 [CHANGELOG.md](../CHANGELOG.md)）。但「烘焙進去」不等於「驗證過」。

### 為什麼這件事重要

比聽起來輕微，關鍵在於它會怎麼表現出來。
`classify_glyph` 會拒絕任何「第二名距離不到 `MIN_MARGIN`」的字形，
所以一個 App 畫的 `7` 若跟 Arial 來源的範本對不上，會被回報成
**讀不出來**，而不是被誤讀成別的數字。
接著 Patches 會把那個標籤退回成「大小不限」，
只有在切法仍然唯一時才接受答案；Zip 則會在「編號必須連續」的檢查上失敗。

所以現實中最壞的情況是「拒絕求解」，不是「給出錯誤答案」。
這正是預期的行為 —— 但它沒有被測試過，而且拒絕求解終究還是失敗。

### 計畫

1. **拍到一張含有它們的盤面。** 一題有 7 個以上編號圓點的 Zip，
   或一個數字是 7 的 Patches 標籤就夠了。這種題目是會出現的，
   只是還沒有人截到。
2. **把那張截圖接進答案表後執行 `python tools/calibrate_digits.py`。**
   這支腳本會拒絕寫出缺少 0-9 任何一個數字的範本集合，所以不會退步。
3. **把素材加進 `tests/test_recognition.py`**，
   並依慣例在 docstring 說明它守住的是什麼。

卡在「還沒有那張截圖」，不是卡在程式。

## 六、其他值得做的小事

| 項目 | 理由 |
|---|---|
| **取得含有 0 與 7 的測試素材** | 這兩個範本來自字型，從未對照真實盤面驗證。一題有 7 個以上圓點的 Zip，或一個數字是 7 的 Patches 標籤就可以 |

| **偵測頁面縮放比例** | 棋盤低於 500px 時辨識會退化。現在只會警告；未來可以直接偵測縮放比例，並建議該按幾次 `Ctrl` `+` |

## 不打算做的事

- **DOM 自動化。** 直接讀 LinkedIn 的 HTML 會比讀像素簡單也穩健。
  但那會把這個專案有趣的那一半刪掉，而且會綁在隨時可能改變的 markup 上。
  見 [DESIGN.zh-TW.md](DESIGN.zh-TW.md#刻意沒有做的事)。
- **用視覺模型做辨識。** 同樣的理由 —— 那是用「不回答」來回答問題，
  而且會替一個目前兩者都不需要的工具，加上網路依賴與 API key。
- **跨平台的螢幕控制。** 圖片模式本來就到處都能用。
  螢幕模式用到 Win32 的視窗聚焦，移植到 macOS 或 Linux 要花不少工，
  換來的功能卻只是重複一件使用者用截圖就能做到的事。
- **把辨識門檻值開放成設定。** 每一個都是在真實盤面上量測出來的，
  而且量到的數值就寫在旁邊。做成設定畫面等於在邀請大家用猜的去調 ——
  正確的解法是上面的第 2.1 項，把它們變成自適應的，這樣就沒有東西需要調。
